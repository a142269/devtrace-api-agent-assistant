# DevTrace——开发者平台 API 接入 Agent 助手

[English](#english) | [中文](#中文)

## 中文

面向开发者 API 接入排障的单 Agent 项目。这是一个独立运行的开发者支持项目，围绕三类可复现问题演示受约束的多步 Agent 流程：**401 鉴权失败、429 限流、Webhook 投递失败**。

Agent 从会话记忆和历史证据开始，生成诊断计划，调用文档、请求记录、密钥权限或 Webhook 工具，并将每次观察写入状态。模型可以在服务端的证据和依赖约束内改变行动顺序；服务端负责工具白名单、参数来源、工单授权、脱敏与失败降级。

> **评审/面试入口（5 分钟）**：先看 [项目速览 PORTFOLIO.md](PORTFOLIO.md) → [架构说明](docs/ARCHITECTURE.md) → [5 分钟演示脚本](docs/DEMO.md) → [面试问答](docs/INTERVIEW.md) → [简历段落](docs/RESUME.md)。最终验收与限制见 [最终验收](docs/FINAL_REVIEW.md)（已入库）；发布 tag：`demo-2026-10-23.1`。

### 技术亮点

- **ReAct 与 Plan-and-Execute**：显示计划提议、服务端批准计划、工具行动、观察和状态变化；行动选择优先使用模型原生 tool calling（失败回退 JSON/规则），不展示内部推理。
- **候选计划评分**：启用 `DEVTRACE_PLANNING_CANDIDATES` 后，对 approved / evidence-first / minimal 三种安全排序按证据覆盖、记录先于文档、依赖合法和长度打分，选终高分执行，响应暴露候选与分数；11 条规则评测 11/11。
- **提示词版本化**：系统/计划/行动/原生工具/重试提示词集中到 `prompts.py`，带 `PROMPT_VERSION`、渲染快照与契约回归；CI 检测未审阅的提示词改动，`GET /developer/prompts` 只暴露版本与大小、不泄露正文。
- **标准 MCP 接入**：内置 JSON-RPC 2.0 的 MCP server/client（`initialize / tools/list / tools/call`，含 stdio 入口，线格式为 **UTF-8 换行分隔 JSON**：服务端显式 `reconfigure(encoding='utf-8')`、客户端起子进程时强制 `PYTHONUTF8=1`，中文工具描述不依赖调用方区域设置）。server 托管 **8 个只读工具**（平台文档、限流文档、请求记录、关联请求、密钥状态、Webhook 投递、公开文档、错误手册），`create_support_ticket` 始终留在本地——它需要用户显式授权和只有本服务持有的会话/幂等上下文。`DEVTRACE_MCP_PUBLIC_TOOLS=enabled` 时公开 API 路径走 MCP，`DEVTRACE_MCP_ALL_TOOLS=enabled` 时 `auth`/`quota`/`webhook` 的读工具全部走 MCP；计划、执行与证据校验按基础工具名比较，因此两种传输共用同一套依赖与门禁规则，MCP 调用失败记为失败步骤而不是静默回落本地工具。规则模式公开路径评测 10/10。
- **外部 MCP server 注册表（可选）**：`DEVTRACE_MCP_SERVERS` 以 JSON 声明 stdio 进程，工具注册为 `ext_<server>_<tool>`；默认拒绝——只有读语义名称且无写提示的工具才注册，与内置同名则跳过，server 连接失败只跳过它自己；`user_id`/`conversation_id`/`idempotency_key`/`ticket_id`/`api_key` 从 schema 移除且每次调用再过滤，绝不转发给第三方进程。空配置或非法 JSON 不启动任何子进程。
- **分层记忆与管理**：Redis 保存工作记忆与未完成计划；ChromaDB 保存隔离的情景记忆、用户画像和开发者文档；提供记忆导出与"遗忘会话"接口（清工作记忆/摘要/情景/计划检查点），并有压缩/导出/遗忘管线质量检查。
- **记忆生命周期与真实质量评测（P5，评分口径 P6 改造）**：Redis 侧工作记忆与摘要的过期时间由 `DEVTRACE_MEMORY_TTL_SECONDS` 配置（默认 86400 秒，下限 3600，非法或未设置回落默认；Docker 实测 86400 / 7200 / 60→3600 三种取值都落到真实 Redis TTL）；ChromaDB 的情景记忆与用户画像**不过期**，只能通过显式 API 删除——`DELETE /developer/memory/{id}` 清会话，`DELETE /developer/profile` 只清调用者本人的画像（含历史格式文档），返回 `profile_deleted`/`workspace` 并写审计事件 `memory.profile_delete`，不触碰会话消息与情景记忆。记忆导出新增 `exported_at` 与 `workspace`，不返回内部画像文档 id。真实模型摘要质量由 `developer/evaluate_memory_quality_live.py` 评测（10 场 × 22 轮合成长对话、每场埋 3 个事实，只走生产压缩提示词）：评分**按事实类别判定并同时报告两列**——`strict` 要求请求编号、`密钥前缀:权限`、结论整句逐字命中；`semantic` 仍要求请求编号逐字，权限允许同义动作表述，结论按概念组命中且命中前做否定检查（"未过期"绝不计为保留"过期"）。门禁只看 `semantic`。同一 provider（`deepseek-chat`）真实复跑：编号 10/10、密钥权限 10/10，结论 `strict` 6/10、`semantic` 10/10，完美场次 `strict` 6/10 / `semantic` 10/10，0 编造标识符、0 超长摘要（终长 139 字），平均 984.9ms；strict 失分的 4 场逐条核对为标点合并与同义替换而非事实丢失。该评测仍刻意不进 CI（会花真实调用），结论概念组与样本都由作者模板生成、单一 provider，`semantic` 满分不等于事实被完整复述。
- **可追溯工具调用**：版本化文档检索、脱敏请求记录、密钥权限摘要、Webhook 投递记录和幂等工单。
- **公开 API 文档知识库**：内置 641 条文档——29 条官方摘要（GitHub、Stripe、OpenAI、DeepSeek、Anthropic、Gemini、通义千问、Twilio、Petstore、通用 429/503）+ 612 条从 Stripe 官方 OpenAPI 完整规格（MIT）导入的接口定义；支持按 API 检索并引用来源，提供 OpenAPI/Markdown 导入工具，且不连接真实平台。
- **错误处置手册**：Stripe、GitHub、Twilio 共 36 条结构化错误条目（401/403/429/400/404/409/5xx、Webhook 验签与投递），每条含症状词、含义、是否可重试、退避策略、恢复步骤和官方来源；40 条症状评测规则模式 40/40。
- **证据驱动诊断**：多条带来源的假设，区分"被观察支持""被证据否定""仅观察到"；请求记录与密钥状态互相矛盾时显式报告证据冲突，关联请求成功时用排除法而不是默认因果关系。
- **安全边界**：API Key 脱敏，工具参数从用户输入或已观察记录取得；工单必须由用户明确授权；用户文本与工具观察中的指令会在时间线中标记为不可信数据，不会作为工具指令执行。依赖侧已做漏洞核查：ChromaDB 3 条漏洞上游暂无修复版本，保持内部网络隔离并加了 CI 审计门禁，详见[依赖与安全评估](backend/developer/依赖与安全评估_2026-10-18.md)。
- **RBAC 与审计日志**：`DEVTRACE_ADMIN_USERS` 定义管理员（服务端判定，角色不进 JWT）；Redis Stream `developer:audit` 应用层只追加登录、chat、任务、工具调用、记忆与提示词事件，`detail` 走字段白名单并对疑似密钥脱敏，绝不含消息正文或工具结果；`GET /developer/audit`（仅管理员，终新优先、limit 1–200、用户/事件过滤）。审计写入 best-effort，Redis 故障不阻断任何主流程。Redis 不是 WORM 存储，该日志定位是"应用层只追加的运维审计"，不是不可篡改存证。
- **工作区隔离（P2）**：`DEVTRACE_USERS_JSON` 支持 workspace 感知的新格式（`{"user": {"password": "...", "workspace": "acme"}}`），旧格式完全兼容并归入 `default`；workspace 由服务端配置解析，**不写入 JWT**。run/task 记录携带归属 workspace，跨 workspace 读取一律 404（不泄露存在性）；审计事件带 workspace 字段（旧事件视为 `default`），管理员查询支持 `?workspace=` 过滤。记忆仍按 user+conversation 隔离，workspace 只是上层归属；未做共享 workspace 成员/协作，也未按 workspace 重新分区 ChromaDB。
- **工程化验证**：开发者 Agent 自动化测试 371 项 + 219 个 subtest（2026-10-18 起为 150 项，随 P2–P14 逐阶段增加）；独立 holdout 集 40 条（原 19 条 + P6 新增 21 条，覆盖冲突/注入/异常/多轮/公开文档），**标签全部由项目作者手写、不是第三方隐藏基准**——规则模式 40/40（原批 19/19、新批 21/21，结果按 `batch` 分别标注，CI 跑整表规则模式），真实模型模式在 **P8 跑满全量 40 条得 37/40**（原批 **19/19**、新批 **18/21**，`eval_holdout_model_2026-10-22_full40.json`；43 次 HTTP 请求、0 重试、0 基础设施失败、墙钟 487.3 秒、单请求 mean 11321.6ms，provider 未返回 usage 因此只披露请求数与时间、不估算 token 成本；P6 那轮为控成本只跑新批 21 条得 18/21，两轮新批结果一致）。3 条失败原样保留并在案例里加 `label_scope` 说明、断言未因结果而修改：2 条是标签按本地工具拼写断言、而 base compose 默认的 `DEVTRACE_MCP_PUBLIC_TOOLS=enabled` 让实际工具带上了 `mcp_` 前缀（本轮 `DEVTRACE_MCP_ALL_TOOLS` 未设置仍原样复现，说明触发条件是默认的 PUBLIC_TOOLS 而非 ALL_TOOLS；P6 归因已在评测报告中就地更正），1 条是模型未带回 v1 版本文档那条具体证据；模型仍只有一个 provider；12 条跨轮任务记忆评测（恢复 vs 重开均 12/12，恢复模式少约 0.91 次重复文档检索）；轻量并发/负载验证（rules 模式、零付费调用、单机 Docker + 2 worker）：10 并发 `/developer/chat/stream` 10/10 收到 `complete`，时延 p50 1049ms / p95 1859ms，首事件 p50 29ms，`run_id`/`task_id` 无重复，同会话并发 1×200 + 2×409、同幂等键并发 1×200 + 2×409 且完成后重放复用同一 `run_id`，同步 `/developer/chat` 36 次得到 26×200 + 10×429 与 30/min/user 窗口一致；P6 那一轮实测到的"流式入口绕过 `limit()`"（24 次流式请求 0 个 429）已在 **P7 修复并复验**：单次流式请求只消耗 1 个配额，31 并发流式 = 29×200 + 2×429 且全部带 `Retry-After: 60`，被拒请求不产生任务记录、不入队、不发 `started` 事件，烧完配额后的同步请求同样 429（共用同一把 `developer:chat-limit:<sha256(user)>`），队列化与进程内 SSE 两条路径各实测一轮；**P8 再把同一语义放到真实 provider（`DEVELOPER_MODEL_MODE=anthropic`）下复验**：不为烧配额而发 31 条会进模型的请求，改为把计数预置到 30（`EX 60`）后只发 1 条流式 + 1 条同步请求，两者都 429 + `Retry-After: 60`，任务/运行/幂等缓存/任务事件四类 Redis key 增量与 worker `task enqueued` 日志增量全为 0，拒绝体与 `chat.rate_limited` 审计 `detail` 不含消息正文，429 时延 3.7ms/46.9ms 对同栈模型执行 mean 11321.6ms——拒绝确实早于模型调用（`eval_stream_limit_model_2026-10-22.json`）；前端 429 提示也已在浏览器实测渲染；2026-10-18 已在本机 Docker 全栈复验规则模式 HTTP 30/30、SSE、断流释放锁、并发 409 与跨轮恢复，并用 Playwright 在桌面/移动端完成联调，另做键盘导航、焦点可见、抽样对比度（WCAG AA）与基础性能检查。这些是小样本、单 provider、单机演示级验证，不构成生产就绪结论。历史评测结果详见评测报告。
- **组合故障与运行记录**：`delivery_combo_01` 会触发关联请求与限流文档检查；登录后可查看终近运行，逐步观察工具执行，并查看模型及工具调用耗时。
- **流式入口限流与 Redis TTL 收敛（P7）**：`/developer/chat/stream` 在进入流或入队**之前**扣减与同步 `/developer/chat` 相同的用户级配额（`developer:chat-limit:<sha256(user)>`，30 次/60 秒），一次流式请求只消耗 1 个配额；超限直接返回 HTTP **429 + `Retry-After: 60`**（不是流内 `error` 事件），且不创建任务记录、不入队、不写 `started` 事件——边界是"连接建立之后不再中途限流"，长连接的续传/重试语义不变。同步入口的 429 同样补上 `Retry-After`。被拒请求写一条 `chat.rate_limited` 审计事件，`detail` 只含白名单字段（`kind`/`status`/`reason_code`），不含消息正文。任务记录、计划检查点、运行记录与运行历史索引、幂等结果缓存、任务事件流这些**瞬时 Redis 数据**的过期时间统一到 `DEVTRACE_REDIS_TTL_SECONDS`（`developer/ttl.py`，默认 86400、下限 60、非法或空值回落默认；Docker 实测默认 86400 与注入 120 都落到真实 key TTL），与记忆 TTL `DEVTRACE_MEMORY_TTL_SECONDS`（下限 3600）保持两个独立开关。
- **评测复验（P8，2026-10-22）**：只增加证据、不改产品代码/提示词/案例/标签/阈值/评分逻辑。真实模型（`deepseek-chat`，Anthropic 兼容端点）跑满 **40 条 holdout：37/40**（原批 19/19、新批 18/21），每条只发一次、0 重试、0 基础设施失败，3 条失败逐条给出根因分类（2 条标签绑定传输拼写 + 1 条具体证据未命中）并原样保留；真实 provider 下复验流式 429 用"预置配额 + 只发 2 条"的方式取证，避免为此烧掉 31 次模型调用。

### 本地运行

1. 在 `backend/` 执行 `python setup_local.py`，创建本地演示账号和密钥配置；已有 `.env` 不会覆盖。

3. 在 `backend/` 执行 `docker compose up -d --build`。若构建网络无法访问 ChromaDB 的 ONNX 模型地址，可先 `docker compose build --build-arg PRELOAD_ONNX=false`，再执行 `docker compose up -d`；此时使用独立 ChromaDB 服务端的嵌入能力。
4. 在 `frontend/` 执行 `npm ci && npm run dev`。若后端不在默认 8000 端口，用 `VITE_PYTHON_API_URL` 指定，例如 `$env:VITE_PYTHON_API_URL='http://127.0.0.1:18002'; npm run dev -- --port 5174`。
5. 登录后使用 `req_auth_01`、`req_quota_01` 或 `delivery_01` 演示。

接口使用本地配置账号登录并签发短期 JWT，身份由服务端验证；管理员角色由 `DEVTRACE_ADMIN_USERS` 服务端判定，`GET /developer/audit` 返回应用层只追加的审计事件；同一用户的会话通过 Redis 锁防止并发覆盖，重复请求可携带 `Idempotency-Key`。模拟平台仅在 Compose 内部网络访问。用户可归属到服务端配置的工作区（跨工作区读取 404、审计按工作区过滤），但这仍是本地演示：没有共享工作区的成员/协作、生产身份服务与真实业务权限，ChromaDB 也未按工作区分区。

## English

DevTrace is a portfolio-ready developer API diagnosis agent. It demonstrates constrained multi-step planning, ReAct-style tool use, Redis/ChromaDB memory, evidence-backed answers, and a Vue visualization for 401 authentication, 429 rate-limit, and Webhook delivery failures.

The project intentionally uses a local mock platform and masked records. It does not connect to production accounts, logs, or ticketing systems.

**演示与生产差距（结论）**：本项目是可在单机 Docker 复现的能力演示，不是生产就绪系统。已验证的边界包括：单租户 + 单 Redis + 单 Chroma 容器（workspace 只是归属与可见性边界，未按租户物理分区）；审计是应用层只追加、Redis 不是 WORM 存储；ChromaDB 0.5.23 有 3 条上游未修复漏洞，只能靠内网隔离与 CI 审计门禁（见依赖与安全评估）；Chroma 侧没有 TTL，情景记忆自 P10 起由 `python -m developer.memory_retention --days N` 做显式保留（默认 dry-run、需人工或外部调度触发，画像仍只能经 API 显式删除）；外部 MCP server 只用自带 fake server 在单测里验证过，未接入真实第三方进程；评测标签由项目作者手写、样本小、模型只来自一个 provider；负载验证是 rules 模式 n=10 的存在性检查；故障恢复只验证过**单点** worker 被 `kill -9` 后由幸存 worker 按租约回收重跑（P12：租约取下限 30 秒、单次而非连环、终态是 `waiting` 而非 `completed`），Redis/Chroma 故障切换与多副本 API 未验证；P12 取证到的两个会话锁缺口已在 **P13 修复**（会话锁改为按锁值里的 `task_id` 做 Lua 比较后删，晚到的清理不会再放走别的任务；回收耗尽重试的终态会 owner-aware 释放锁并补写恰好一条 `task.finished`），但修复只验证到单元级 + 真实 Redis 上的 Lua 原语，**回收终态路径未在真实栈上跑过**（没有向真实队列注入合成任务），连环 kill 与"kill 落在写运行记录瞬间"的分相演练同样未做；同类"僵尸锁"形状还有两处（`task_queue.recover_running_tasks()`、`api/main.py` 的 `reconcile_stale_tasks`/`_mark_interrupted`）P13 按范围纪律只记录未修，已在 **P14 收掉**：两处终态（启动恢复耗尽重试、被判 `interrupted`）现在都会按锁值 `task_id` 做 owner-aware 释放并写恰好一条 `task.finished`（`interrupted` 的 `detail` 另含 `reason_code`），缺 `user_id` 或会话时**跳过释放而不是猜 key**，重复 reconcile 不再二次审计或二次释放。P14 的验证同样停在单元 + fake Redis 一层（卡片禁止本轮起 Docker、零模型调用），**这两条路径的端到端真实栈验证仍未做**；此外 `task_queue.dead_letter()` 至今没有生产调用方（已标注为死代码，删除留给下一轮裁定），worker 心跳过期但进程仍在计算时仍存在一条很窄的"同任务两条终态审计"窗口（`_mark_interrupted` 的写前重读只缩小而非原子化该窗口）。流式入口自 P7 起与同步入口共用 30 次/60 秒用户级限流（P8 已在真实 provider 下复验拒绝路径无副作用、且早于模型调用），但限流窗口仍是单 Redis 固定窗口、没有按 IP/租户分层配额，也没有网关级限流；Redis 不可达或 Lua 脚本抛错时，限流器自 P10 起对基础设施异常 fail-open 并写审计（不是全量 500），但这是可用性优先的演示级取舍，故障窗口内配额不再生效，且 chat 主流程仍依赖 Redis 会话锁。身份服务、TLS、密钥轮换、生产限流与容灾均未实现。
