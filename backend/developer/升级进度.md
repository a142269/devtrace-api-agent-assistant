# DevTrace 升级进度与验证边界

本次升级基于提供的六周方案。以下记录代码实际实现，未完成项不视为已经达到生产级。

## 已实现

- 服务端签发短期 JWT，本地账号使用 PBKDF2 密码摘要；诊断和运行记录从 token 获取身份，不接受客户端自报 `user_id`。登录和聊天通过 Redis 固定窗口限流（聊天为 30 次/60 秒；自 2026-10-22 P7 起，同步 `/developer/chat` 与流式 `/developer/chat/stream` 共用同一把用户配额，超限时两条入口都返回 429 + `Retry-After: 60`），CORS 使用配置的来源。
- 同一用户和会话通过 Redis 锁互斥；不同请求冲突返回 409。`Idempotency-Key` 可以重放已完成请求结果，并拒绝同键不同内容。工单另有自己的业务去重。
- 认证诊断根据模拟请求记录添加或跳过密钥权限工具；`diagnosis` 使用成功工具观察生成带来源的结果。这里是有限的规则与模型协作，不是完全开放的假设搜索。
- 文档检索加入小规模 BM25 词法检索、向量检索、RRF 融合和技术词精确匹配规则重排；两路检索在召回时按版本和 active 状态过滤。`req_auth_v2_01` 通过请求记录确定版本后使用 v2 文档；目前只有一个 v2 诊断案例，尚未实现学习型重排、多 SDK 和完整 v2 场景。
- 固定基线标签已移到独立 JSON，评测记录诊断、证据和工具数量，并区分模型、规则及降级。基线依然与模拟数据共享案例，不能证明泛化能力。
- 现有 CI 加入 Ruff 检查和覆盖率输出；模拟平台默认不映射外部端口。画像更新改为有超时的同步尝试，没有构建可靠队列。
- 使用 SSE 逐条展示计划、行动与观察；前端可以停止当前 HTTP 请求。断开连接会取消执行并释放会话锁；每步开始前保存可恢复检查点，用户可在同一会话继续。流式任务状态按用户保存在 Redis，支持查询 running、waiting、completed、failed、cancelled、interrupted。任务记录带 `updated_at` 心跳（发出 SSE 事件和无事件 15 秒空闲心跳都会刷新），查询时若 `running` 超过 240 秒未更新会改为 `interrupted`（阈值高于 150 秒执行上限和 180 秒会话锁，避免误判）；进程启动时还会扫描 `developer:tasks:running` 索引，把上一个进程残留的 `running` 一并修正，该修复只适用于单进程/单副本共享 Redis。持久任务队列自 2026-10-19（P3）起由 `DEVTRACE_TASK_QUEUE` 控制、Compose 默认 `enabled`；进程内 SSE 路径仍不会自动重跑中断任务，需要同一会话发送"继续"。
- 断流清理已按真实 HTTP 行为加固：Starlette 在客户端断开时会取消整个响应任务，普通 `finally` 中的状态写入和 Redis 锁释放会被一并取消。现在用独立 shielded 任务落 `cancelled` 状态，并用 `asyncio.shield` 释放会话锁；2026-10-18 的 Docker 全栈验证确认断流后消息立即为 `cancelled`、同一会话可继续。
- 新增 10 条生成的组合案例 `delivery_combo_01` 至 `delivery_combo_10`：投递记录提供关联请求 ID，执行器据此追加请求核验；实际观察到 429 后再检索限流文档。两条记录分别形成证据，关联关系不等于证明二者存在因果关系。这些案例共享生成规则，不能当作独立泛化评测集。
- 最近运行按认证用户建立 Redis 索引，保留最多 100 条、有效期由 `DEVTRACE_REDIS_TTL_SECONDS` 决定（自 2026-10-22 P7 起统一配置，默认 86400 秒即 24 小时、下限 60 秒），接口返回最近 50 条；前端可查看和恢复会话。每轮报告工具耗时、模型 API 调用耗时与服务端返回的 Token 用量；未返回的 Token 显示为未知。
- 区分记录 404、空文档和工具不可用，后两种情况可用同一标识继续重试。运行时间线在工具开始前发送行动事件。
- 将证据目标、工具依赖和计划批准逻辑抽离到 `developer/planner.py`；诊断结论由 `developer/verifier.py` 根据观察结果构建。执行编排仍集中在 `developer/assistant.py`。
- 新增 12 条人工标注的公开检索查询，以及 `python -m developer.evaluate_retrieval --output <报告路径>`：对同一语料比较 Dense、Hybrid 和规则重排，记录 Recall@K、MRR 和每条候选结果。语料与标签很小且公开，不能证明泛化；需实际运行后才能引用数值。
- 诊断从"单条根因标签"扩展到多假设结构：`developer/verifier.py` 为每条假设记录 `status`（supported / contradicted / observed）、`confidence`、证据来源、`contradicted_by`、`next_evidence` 和 `remediation`。请求记录与密钥状态记录互相矛盾时输出 `conflicting_evidence`，不再默认采信其中一侧；投递记录关联的请求成功时，明确写"可排除限流/鉴权作为投递失败原因"，把关联关系与因果关系分开。来自关联请求的失败只记为 `observed`/`scope=related_request`，不再当作投递失败的根因，也不再据此给出无关的 Retry-After 建议。这些判断仍由固定规则完成，不是开放式假设搜索。
- 新增 `developer/security.py`：扫描用户文本和工具观察中的指令覆盖、凭证索取、越权授权、系统提示泄露等模式。命中后只在响应 `security` 字段和时间线中披露，观察里的指令不会被执行；工具结果中的疑似指令也不会原样进入诊断描述和答复。模型系统提示同时声明工具观察与用户文本是不可信数据。检测是正则启发式，不是完整注入防护。
- 新增本地诊断/安全夹具（不加入 `EVAL_CASES`，30 条固定基线保持不变）：`req_auth_11`（记录称凭证过期、密钥记录却为 active）、`delivery_combo_11` + `req_ok_01`（关联请求成功，用于排除法）、`delivery_inject_01`（记录错误摘要里带指令）。
- 自动化测试从 35 项扩展到 107 项，新增 `tests/test_diagnosis.py`、`tests/test_security.py` 与任务状态修复用例；新增 `python -m developer.evaluate_diagnosis` 复跑冲突、关联排除与注入样例。CI 的 Ruff 检查范围同步加入新文件。

- 真实 HTTP 流式请求返回 11 个时间线事件与完成事件；断开流时释放锁由自动化测试验证。
- 前端生产构建通过；自动化测试和覆盖率以本次实际执行结果及 CI 为准。

- 规划对照：在同一 30 条公开模拟案例上，固定检查与条件检查均通过 30/30，适用的根因标签均为 20/20；平均工具调用分别为 2.33 和 2.23 次。[原始报告](eval_planning_2026-10-17.json)。两组都是规则模式，并仅比较认证头错误时是否跳过权限检查，不能解释为模型自主规划能力的提升。
- 故障注入：20 次人造异常或立即抛出的超时中，20 次均报告等待，用户发送“继续”后 20 次均恢复；[原始报告](eval_recovery_2026-10-17.json)。故障都被设定为下一次调用即可恢复，使用进程内模拟服务和假 Redis；计时不代表真实网络超时或生产性能。
- 真实模型样例：使用配置的 `deepseek-v4-pro`，四条公开模拟案例（401、429、Webhook、组合故障）均为 `model` 决策且通过对应检查；[原始报告](eval_live_samples_2026-10-17.json)包含实际 Token 和耗时。工具和记忆使用测试替身，四条样例不足以估计模型准确率或线上性能。

- 记忆对照：隔离 Redis 与本地 ChromaDB 中，10 条同会话案例的标识召回为无记忆 0/10、短期记忆 10/10、分层记忆 10/10；10 条新会话案例分别为 0/10、0/10、10/10；20 次跨用户检查未发现目标标识泄漏。见[原始报告](eval_memory_2026-10-17.json)。历史摘要直接写入，测试仅衡量合成上下文中的标识召回，不衡量模型摘要、画像质量或诊断成功率，也不能证明全面隔离。
- 依赖扫描：升级前使用 pip-audit 2.9.0 扫描，报告 5 个包共 34 条漏洞记录；见[原始报告](dependency_audit_2026-10-17.json)。升级 JWT、FastAPI、Starlette、multipart 和 dotenv 后，完整依赖复扫汇总为 1 个包的 3 条记录（此次 JSON 未保存）；另一次[直接依赖复扫](dependency_audit_direct_2026-10-17.json)确认 ChromaDB 0.5.23 的 PYSEC-2026-3813、3814、3815 未列出修复版本。直接依赖报告不包含传递依赖，必须继续跟踪并检查 CI 完整扫描报告。扫描是版本匹配提示，并不证明每条漏洞均可利用，也不能说明其余风险为零。

## 队列生产化与可观测性（2026-10-19，P3）

只用 Redis 原语（List / 有序集合 / `SET NX` / `SCAN`），没有引入 Celery、RabbitMQ、Kafka 或任何新中间件；前端、JWT、workspace 语义与既有审计字段白名单均未改动。

- 优先级队列：`developer:tasks:queue:high|normal|low`，`enqueue(..., priority='normal')` 未知取值抛 `ValueError`；旧 `developer:tasks:queue` 保留为最后一级，供历史入队与外部脚本使用；worker 改为多键 `BRPOP(high, normal, low, legacy, timeout)`。任务记录新增 `priority`，回收/重放都回到原优先级。语义边界：**空闲 worker 会在键被写入的瞬间醒来**，所以严格优先级只在任务同时积压、worker 忙于执行时成立（已用 `--scale worker=0` 预排队做确定性验证，完成顺序 high→normal→low→legacy）。
- 租约：running 记录写 `lease_id`（worker 标识）与 `lease_until`（epoch 秒）；`DEVTRACE_TASK_LEASE_SECONDS` 默认 90、下限 30、非法值回落默认（只写进 `.env.example` 注释）。worker 后台每 30 秒续期，且仅当"仍持有该租约且状态为 running"时写入；`reclaim_expired()` 扫任务索引，只处理 `running` 且 `lease_until` 已过期的记录，用 `SET NX EX 30 developer:task-reclaim:{id}` 互斥锁 + 二次校验保证多 worker 只回收一次，回收后 `attempts+1` 进延迟队列、耗尽次数进死信并清租约。**没有租约字段的旧记录不参与租约回收**，仍由 P2 的 worker 启动时"owner 已消失"回收兜底。`GET /developer/tasks/{id}` 隐藏 `lease_id/lease_until`（内部主机名-PID）。

- 死信与重放（仅管理员）：`GET /developer/dead-letter?limit=1..200` 返回 `task_id/status/attempts/error/workspace/priority/trace_id` 摘要（error 再做一次疑似密钥脱敏并截断 200，绝不含消息正文）；`POST /developer/tasks/{id}/replay` 只对"在死信列表且状态为 failed"的任务生效——重置 `attempts=0`、清 error 与租约、回到原优先级队列，写 `task.replayed` 审计。**非 ok 结果（不存在 / 不在死信 / 状态不是失败）统一返回 409**，不区分原因，避免通过状态码差异泄露任务存在性；重放失败同样落审计并带 `reason_code`。非管理员 403、匿名 401。
