# DevTrace 升级进度与验证边界

本次升级基于提供的六周方案。以下记录代码实际实现，未完成项不视为已经达到生产级。

## 已实现

- 服务端签发短期 JWT，本地账号使用 PBKDF2 密码摘要；诊断和运行记录从 token 获取身份，不接受客户端自报 `user_id`。登录和聊天通过 Redis 固定窗口限流，CORS 使用配置的来源。
- 同一用户和会话通过 Redis 锁互斥；不同请求冲突返回 409。`Idempotency-Key` 可以重放已完成请求结果，并拒绝同键不同内容。工单另有自己的业务去重。
- 认证诊断根据模拟请求记录添加或跳过密钥权限工具；`diagnosis` 使用成功工具观察生成带来源的结果。这里是有限的规则与模型协作，不是完全开放的假设搜索。
- 文档检索加入小规模 BM25 词法检索、向量检索、RRF 融合和技术词精确匹配规则重排；两路检索在召回时按版本和 active 状态过滤。`req_auth_v2_01` 通过请求记录确定版本后使用 v2 文档；目前只有一个 v2 诊断案例，尚未实现学习型重排、多 SDK 和完整 v2 场景。
- 固定基线标签已移到独立 JSON，评测记录诊断、证据和工具数量，并区分模型、规则及降级。基线依然与模拟数据共享案例，不能证明泛化能力。
- 现有 CI 加入 Ruff 检查和覆盖率输出；模拟平台默认不映射外部端口。画像更新改为有超时的同步尝试，没有构建可靠队列。
- 使用 SSE 逐条展示计划、行动与观察；前端可以停止当前 HTTP 请求。断开连接会取消执行并释放会话锁；每步开始前保存可恢复检查点，用户可在同一会话继续。流式任务状态按用户保存在 Redis，支持查询 running、waiting、completed、failed、cancelled、interrupted。任务记录带 `updated_at` 心跳（发出 SSE 事件和无事件 15 秒空闲心跳都会刷新），查询时若 `running` 超过 240 秒未更新会改为 `interrupted`（阈值高于 150 秒执行上限和 180 秒会话锁，避免误判）；进程启动时还会扫描 `developer:tasks:running` 索引，把上一个进程残留的 `running` 一并修正，该修复只适用于单进程/单副本共享 Redis。仍没有持久任务队列，也不会自动重跑中断任务。
- 断流清理已按真实 HTTP 行为加固：Starlette 在客户端断开时会取消整个响应任务，普通 `finally` 中的状态写入和 Redis 锁释放会被一并取消。现在用独立 shielded 任务落 `cancelled` 状态，并用 `asyncio.shield` 释放会话锁；2026-10-18 的 Docker 全栈验证确认断流后消息立即为 `cancelled`、同一会话可继续。
- 新增 10 条生成的组合案例 `delivery_combo_01` 至 `delivery_combo_10`：投递记录提供关联请求 ID，执行器据此追加请求核验；实际观察到 429 后再检索限流文档。两条记录分别形成证据，关联关系不等于证明二者存在因果关系。这些案例共享生成规则，不能当作独立泛化评测集。
- 最近运行按认证用户建立 Redis 索引，保留最多 100 条、有效期 24 小时，接口返回最近 50 条；前端可查看和恢复会话。每轮报告工具耗时、模型 API 调用耗时与服务端返回的 Token 用量；未返回的 Token 显示为未知。
- 区分记录 404、空文档和工具不可用，后两种情况可用同一标识继续重试。运行时间线在工具开始前发送行动事件。
- 将证据目标、工具依赖和计划批准逻辑抽离到 `developer/planner.py`；诊断结论由 `developer/verifier.py` 根据观察结果构建。执行编排仍集中在 `developer/assistant.py`。
- 新增 12 条人工标注的公开检索查询，以及 `python -m developer.evaluate_retrieval --output <报告路径>`：对同一语料比较 Dense、Hybrid 和规则重排，记录 Recall@K、MRR 和每条候选结果。语料与标签很小且公开，不能证明泛化；需实际运行后才能引用数值。
- 诊断从"单条根因标签"扩展到多假设结构：`developer/verifier.py` 为每条假设记录 `status`（supported / contradicted / observed）、`confidence`、证据来源、`contradicted_by`、`next_evidence` 和 `remediation`。请求记录与密钥状态记录互相矛盾时输出 `conflicting_evidence`，不再默认采信其中一侧；投递记录关联的请求成功时，明确写"可排除限流/鉴权作为投递失败原因"，把关联关系与因果关系分开。来自关联请求的失败只记为 `observed`/`scope=related_request`，不再当作投递失败的根因，也不再据此给出无关的 Retry-After 建议。这些判断仍由固定规则完成，不是开放式假设搜索。
- 新增 `developer/security.py`：扫描用户文本和工具观察中的指令覆盖、凭证索取、越权授权、系统提示泄露等模式。命中后只在响应 `security` 字段和时间线中披露，观察里的指令不会被执行；工具结果中的疑似指令也不会原样进入诊断描述和答复。模型系统提示同时声明工具观察与用户文本是不可信数据。检测是正则启发式，不是完整注入防护。
- 新增本地诊断/安全夹具（不加入 `EVAL_CASES`，30 条固定基线保持不变）：`req_auth_11`（记录称凭证过期、密钥记录却为 active）、`delivery_combo_11` + `req_ok_01`（关联请求成功，用于排除法）、`delivery_inject_01`（记录错误摘要里带指令）。
- 自动化测试从 35 项扩展到 107 项，新增 `tests/test_diagnosis.py`、`tests/test_security.py` 与任务状态修复用例；新增 `python -m developer.evaluate_diagnosis` 复跑冲突、关联排除与注入样例。CI 的 Ruff 检查范围同步加入新文件。

## 实测（2026-10-17，本地 Docker）

- 规则模式 HTTP：30/30 通过；适用根因标注 20/20，证据来源检查 30/30，平均工具调用 2.23 次，中位耗时 73.2 ms。结果来自[原始记录](eval_upgrade_rules_2026-10-17.json)，本地固定数据和规则模式不代表真实模型准确率或生产性能。
- 隔离 Redis 上同会话并发结果为 200 和 409；不同账号读取运行记录返回 404；同幂等键重放获得同一个 run_id。
- 真实 HTTP 流式请求返回 11 个时间线事件与完成事件；断开流时释放锁由自动化测试验证。
- 前端生产构建通过；自动化测试和覆盖率以本次实际执行结果及 CI 为准。
- 检索对照：12 条公开模拟查询、K=5，Dense / Hybrid / 规则重排的 Recall@5 均为 12/12，MRR 分别为 0.799 / 0.958 / 1.000。数据和每条排名见[原始报告](eval_retrieval_2026-10-17.json)。各版本只有 2～4 篇文档，因此 Recall@5 容易饱和；该结果不能推断真实检索质量。
- 规划对照：在同一 30 条公开模拟案例上，固定检查与条件检查均通过 30/30，适用的根因标签均为 20/20；平均工具调用分别为 2.33 和 2.23 次。[原始报告](eval_planning_2026-10-17.json)。两组都是规则模式，并仅比较认证头错误时是否跳过权限检查，不能解释为模型自主规划能力的提升。
- 故障注入：20 次人造异常或立即抛出的超时中，20 次均报告等待，用户发送“继续”后 20 次均恢复；[原始报告](eval_recovery_2026-10-17.json)。故障都被设定为下一次调用即可恢复，使用进程内模拟服务和假 Redis；计时不代表真实网络超时或生产性能。
- 真实模型样例：使用配置的 `deepseek-v4-pro`，四条公开模拟案例（401、429、Webhook、组合故障）均为 `model` 决策且通过对应检查；[原始报告](eval_live_samples_2026-10-17.json)包含实际 Token 和耗时。工具和记忆使用测试替身，四条样例不足以估计模型准确率或线上性能。
- 分类回归：规则模式下基础 40/40、组合及多轮 30/30、故障注入 20/20、工单授权与脱敏 20/20；见[逐项报告](eval_scenarios_2026-10-17.json)。这些是 110 条公开的模拟变体，复用同一批记录和规则；安全组只覆盖上述两类检查，不是全面安全评估，更不是独立隐藏测试集。
- 记忆对照：隔离 Redis 与本地 ChromaDB 中，10 条同会话案例的标识召回为无记忆 0/10、短期记忆 10/10、分层记忆 10/10；10 条新会话案例分别为 0/10、0/10、10/10；20 次跨用户检查未发现目标标识泄漏。见[原始报告](eval_memory_2026-10-17.json)。历史摘要直接写入，测试仅衡量合成上下文中的标识召回，不衡量模型摘要、画像质量或诊断成功率，也不能证明全面隔离。
- 依赖扫描：升级前使用 pip-audit 2.9.0 扫描，报告 5 个包共 34 条漏洞记录；见[原始报告](dependency_audit_2026-10-17.json)。升级 JWT、FastAPI、Starlette、multipart 和 dotenv 后，完整依赖复扫汇总为 1 个包的 3 条记录（此次 JSON 未保存）；另一次[直接依赖复扫](dependency_audit_direct_2026-10-17.json)确认 ChromaDB 0.5.23 的 PYSEC-2026-3813、3814、3815 未列出修复版本。直接依赖报告不包含传递依赖，必须继续跟踪并检查 CI 完整扫描报告。扫描是版本匹配提示，并不证明每条漏洞均可利用，也不能说明其余风险为零。
- 候选升级镜像执行 `pip check` 与 35 项后端 unittest 均通过；ChromaDB 测试输出遥测接口兼容警告。该镜像构建与真实服务集成在 2026-10-18 另做了一次本机 Docker 全栈验证，见下文。
- CI 会运行 pip-audit 并上传 JSON 报告；漏洞或扫描失败显示警告，目前不作为阻断发布的安全门禁。查看 CI 日志和报告才能确认扫描是否成功及具体发现。
- 扫描报告描述了 ChromaDB 的跨租户授权缺陷及特定权限下的代码注入风险。独立项目的 Compose 不发布 ChromaDB 端口，但内部网络隔离不能替代修复、身份授权和完整安全评估；不要将演示配置用于生产。旧 EchoMind 的运行容器可能另行发布端口，应检查其独立配置。

- 环境：Docker Desktop（Linux 容器）；独立 Compose 项目 `devtrace-verify`，宿主端口映射 `18002:8000`（`8000/5173` 已被本机其他项目容器占用，未改动它们）；redis 7-alpine、chromadb 0.5.23、developer-sandbox、devtrace 四个容器均 healthy。
- 全新镜像构建：使用当前 Dockerfile 与 `requirements.txt` 从零构建成功，容器内确认 PyJWT 2.15.0 / chromadb 0.5.23 / fastapi 0.143.3 与新代码文件存在。本机网络访问 ChromaDB 的 ONNX 模型 S3 地址会在传输阶段停滞，因此构建时使用 `--build-arg PRELOAD_ONNX=false` 跳过预下载；运行所需模型缓存从本机已有镜像复制进容器（嵌入式兜底模式需要，服务端 ChromaDB 模式不依赖）。普通网络下按默认参数构建即可把模型烘进镜像。
- HTTP 规则模式基线：30/30 通过，证据检查 30/30，适用根因 20/20，平均工具调用 2.23 次，中位耗时 80.0 ms，无规则降级；见[原始报告](eval_docker_rules_2026-10-18.json)。
- 真实模型模式（本地 `.env` 配置的 DeepSeek Anthropic 兼容端点）：401、429、Webhook、组合故障 4 条样例全部 `decision_mode=model`、计划完成、工具与假设正确；组合故障仍是 4 次工具调用、2 条假设、无无关 Retry-After。模型调用次数 3–5 次/请求，Token 用量（入/出）分别约 3154/157、1721/140、1832/135、4944/223，模型耗时 2.3–4.1 s/请求；见[原始报告](eval_model_http_2026-10-18.json)。真实模型 SSE 路径返回 12 个事件、任务 `completed`、`decision_mode=model`、Token 2173/154、客户端 4.1 s；见[原始报告](eval_model_stream_2026-10-18.json)。另用项目判定器每类抽 1 条（共 3 条）跑模型模式：3/3 通过、0 次规则降级、中位 5.0 s；见[抽样报告](eval_model_samples_2026-10-18.json)。样本量很小且依赖外部模型服务，不能当作准确率或线上性能。
- SSE：真实流式请求返回 16 个事件（started、15 个 timeline、complete），任务状态 `completed`。
- 断流：客户端提前断开后任务立即落为 `cancelled`，同一会话立刻可继续并返回 200/complete（会话锁已释放）；见[断言记录](eval_docker_disconnect_2026-10-18.json)与[综合报告](eval_docker_http_2026-10-18.json)。
- 并发与幂等：同一会话两个并发请求返回 200 与 409；同一 `Idempotency-Key` 重放返回同一个 `run_id`，两次均 200。
- 跨轮恢复：首轮缺少标识为 `waiting`，同会话补充 `req_auth_01` 后 `complete`，读取到 2 条最近消息。
- 组合故障与安全：`delivery_combo_01` 按“文档 → 投递记录 → 关联请求 → 限流文档”执行，输出 2 条假设且不再给出无关的 Retry-After；`delivery_inject_01` 被标记为疑似注入、未创建工单；`req_auth_v2_01` 先核验版本再检索 v2 文档。

- 局限：真实模型只跑了 4 条固定样例、1 条 SSE 与 3 条抽样判定，未做大规模模型评测；宿主 `8000/5173` 被其他服务占用，本栈用 18002 端口，前端联调用 5174。

## 依赖安全评估（2026-10-18）

- 结论：`chromadb==0.5.23` 的 3 条漏洞（1 条 CRITICAL 代码注入、2 条 HIGH 跨租户授权）在 OSV 上 `last_affected` 为 **1.5.9（当前最新版）**，**没有修复版本**。因此不升级：升级不能消除漏洞，且 0.5 → 1.x 是客户端/服务端/集合 API 的大版本迁移。
- 暴露面：ChromaDB/Redis/沙箱都不发布宿主端口，只处于 Compose 内部网络；DevTrace 没有启用 ChromaDB 认证/RBAC，是单租户本地演示，不是漏洞描述里的"已认证多租户"形态。这不等于安全，只是明确了边界：不能用于生产、不能接真实租户数据。
- 本轮加固：新增 `developer/audit_gate.py` 作为 CI 门禁——**只阻断存在修复版本的漏洞**，无修复版本继续以非阻断方式展示；新增 `tests/test_deployment_config.py` 回归测试，锁定"内部服务不发布端口、`.env` 不进 Git/镜像、镜像非 root、沙箱健康检查指向 8100"。
- 完整评估、决策和替代方案见 [依赖与安全评估_2026-10-18.md](依赖与安全评估_2026-10-18.md)。

## 尚需完成

- 更大规模、真正第三方独立标注的复杂、多原因、异常和安全评测集；本轮 19 条 holdout 是作者手写的第二套公开集，不是第三方隐藏基准，且模型只来自一个 provider。记忆方面已有 12 条跨轮任务评测，但仍是规则模式、stub 工作记忆，ChromaDB 情景记忆质量、模型摘要和真实任务成功率仍未评估。
- 扩大组合故障与关联记录覆盖；冲突处理目前只有"请求记录 vs 密钥状态"和"投递 vs 关联请求"两类固定规则，尚未实现加权证据、冲突消解策略或模型自主提出竞争假设。
- 队列生产化（多 worker 租约、优先级、延迟重试、指标）与中断任务自动重跑；P1 已提供审计事件流（应用层只追加，非 WORM），但队列语义仍是单 worker 启动时回收。
- 真实租户授权、身份服务、TLS、密钥轮换、业务数据隔离（P2 已提供 workspace 归属/可见性边界，尚无按租户物理分区与共享协作）、生产限流和故障恢复策略。
- 更大规模的独立检索评测、学习型重排、文档生命周期管理、更多 v2 诊断；ChromaDB 漏洞在上游发布修复版本前只能保持隔离和审计门禁，届时需同时升级 Python 包与 `chromadb/chroma` 镜像并重跑检索/记忆/集成测试；提示注入检测需要在模型在线模式下做更充分的对抗评估。
