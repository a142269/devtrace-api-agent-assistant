# 开发者平台 API 接入助手：完整构建与十模块说明

本文按原项目《EchoMind 学习文档》《完整使用指南》《业务流程说明》的写法，把场景定位、架构、代码、构建顺序、运行、验证和面试讲法串起来。**描述以当前代码为准**；图片中的十个模块是核对框架，并不意味着每种举例能力都已实现。

## 1. 场景定位与边界

独立项目的 `/developer/chat` 面向开发者接入排障：输入 401、429 或 Webhook 投递问题，依据 v1 文档和本地模拟平台记录，给出可追溯结论。首版仅有一个主 Agent。

模拟平台内置 10 条鉴权、10 条限流、10 条 Webhook 案例。`req_auth_01`、`req_quota_01` 和 `delivery_01` 可作演示入口。记录、文档和工单均是虚构数据。项目不会连接真实开发者账号、生产日志或工单系统。

核心链路：

~~~text
用户消息
  → FastAPI 参数校验、消息脱敏
  → 读取专属 Redis/ChromaDB 记忆与未完成计划
  → 模型提出故障类别、目标、工具计划
  → 执行器核对最小证据链并创建步骤
  → 选择下一行动 → 工具参数校验/HTTP 调用 → 观察与证据登记
  → 必要时追问、调整一次计划、下一轮恢复
  → 根据成功的观察生成答复和运行记录
  → Vue 展示计划、行动、观察、证据、记忆
~~~

这是一条受约束的 Plan-and-Execute + ReAct 风格循环。模型参与规划与行动选择，合法提议可改变实际工具顺序；服务端负责补齐必需证据和检查依赖。最终文字由已验证的观察数据拼成；它不是开放式自主研究 Agent，也没有展示模型内部推理。

## 2. 项目结构与技术栈

## 3. 按构建顺序理解实现

这一节是从零复现此场景的开发顺序，不是声称历史提交严格按此顺序发生。

### 3.1 定义问题、证据链和模拟数据

先限定故障类型为 `auth`、`quota`、`webhook`，再确定每类问题必须取得的证据：

| 类型 | 最小证据链 | 典型结论依据 |
| --- | --- | --- |
| 401/403 鉴权 | v1 鉴权文档 → `request_id` 请求记录 → 记录给出的 `key_prefix` 权限摘要 | 过期、头格式错误、缺少 scope 等，以记录为准 |
| 429 限流 | v1 速率限制文档 → `request_id` 请求记录 | `limit_per_minute`、`remaining`、`retry_after_seconds` |
| Webhook 失败 | v1 Webhook 文档 → `delivery_id` 投递记录 | 接收端状态、重试次数、脱敏错误摘要 |

`developer/data.py` 生成 30 条可重复案例和四篇 v1 文档。注意鉴权组里包含 403 缺少 scope 的样本，不能把全部 10 条都说成 HTTP 401。

### 3.2 建立独立模拟平台

`developer/sandbox.py` 提供 `GET /mock/requests/{request_id}`、`GET /mock/keys/{key_prefix}`、`GET /mock/webhooks/{delivery_id}` 和 `POST /mock/tickets`。前三项只返回排障所需的脱敏字段，不保存或返回完整 API Key。工单由 SQLite 的唯一 `idempotency_key` 约束保证重复提交得到同一编号。

模拟平台作为独立服务运行在容器端口 8100。Agent 经 `httpx` 调用其 HTTP 接口，这让工具失败、超时与记录缺失可以作为真实的观察结果进入循环。该服务只代表本地演示环境。

### 3.3 建立独立知识库与 Skill

启动时，`api/main.py` 用 `developer.data.DOCS` 初始化 `developer_knowledge`。`KnowledgeBase` 把文档切片并写入 ChromaDB，工具 `search_api_docs` 先检索，再按目标故障类型筛选标题。当前文档版本只有 v1；所谓“版本化”指文档标题和查询携带 v1，尚无多版本索引管理。

`developer/skills/SKILL.md` 给模型注入排障规范：先核对文档、不要仅凭状态码断言根因、不要索取完整密钥、工单需明确授权、答复必须标明模拟数据。Skill 在 API 启动时载入；开发者场景没有独立的热加载接口。

### 3.4 注册工具

`DeveloperAssistant._register_tools()` 注册五个工具：

| 工具 | 输入 | 返回 | 副作用 |
| --- | --- | --- | --- |
| `search_api_docs` | `query`、`top_k` | 文档片段 | 无 |
| `get_request_trace` | `request_id` | 脱敏请求记录 | 无 |
| `inspect_key_scope` | `key_prefix` | 状态和 scope 摘要 | 无 |
| `get_webhook_delivery` | `delivery_id` | 脱敏投递记录 | 无 |
| `create_support_ticket` | `issue_id` | 模拟工单编号 | 写 SQLite |

本地 `MCPToolManager` 对工具做必填字段和基础类型校验、12 秒超时、失败熔断；文档检索可使用 300 秒进程内缓存。开发者工具没有配置自动重试、查询改写或结果重排。类名含“MCP”，**但此场景没有启动 MCP server，也没有执行 MCP 协议握手**；面试时应称为项目内工具管理层。

### 3.5 接入模型、计划与执行器

`AnthropicDecisionModel.make_plan()` 要求模型输出 JSON：`kind`、`goal`、`tools`。执行器用标识符和故障类别再次核对，保留该类别内合法工具的提议顺序，再补齐 `KIND_TO_TOOLS` 规定的最小证据链，并修正依赖顺序。例如 429 可先查脱敏请求再查版本文档；鉴权的权限摘要必须在请求记录之后。`proposed_tools`、`approved_tools` 和 `adjustments` 展示提议与服务端批准结果。

`choose_action()` 在每一步读取计划、已有观察和 `ready_steps`，模型输出下一项 `step_id`、`tool`、`args`。执行器只接受当前满足依赖、标识和授权条件的步骤。真正的 `request_id`、`delivery_id`、`key_prefix` 由用户输入或前一条工具记录提供，避免采用模型编造的标识。模型 JSON 无效或接口失败时使用规则决策，并在 `decision_mode` 与时间线标明降级。

该模式体现“计划 → 行动 → 观察 → 下一步”，但行动空间是受约束的，不是 Tree-of-Thought。也没有使用模型服务原生的 `tool_use` / Function Calling 消息格式；当前是要求模型返回 JSON，再由应用层调用工具。

### 3.6 处理观察、失败和跨轮恢复

每次工具调用写入 `actions` 和 `timeline`：步骤、工具、输入、成功与否、观察摘要、来源、耗时。成功时把来源加入 `evidence` 并将步骤标为 `done`。失败时步骤为 `failed`，最多修订一次计划并追问正确标识；不会把失败调用放进成功证据。单轮最多五次工具行动。

没有 `request_id` 或 `delivery_id` 时，计划状态为 `waiting`。状态以用户 ID 和会话 ID 的组合键在 Redis 保存 24 小时。用户下一轮带相同 `conversation_id` 补充标识后，执行器恢复待完成步骤，保留已取得的文档和观察，避免整条诊断重新开始。

最终回复当前由 `RuleDecisionModel.summarize()` 根据成功工具结果生成；即便 `decision_mode=model`，它表示模型成功参与规划/行动选择，**不表示最终自然语言由模型自由生成**。

### 3.7 接入记忆

开发者 `MemoryManager` 读四类上下文：Redis 最近消息、Redis 压缩摘要、ChromaDB 情景记忆、ChromaDB 用户画像。最近消息上限 20 条，达到 15 条触发压缩并保留最近 5 条；历史召回先限定用户和会话，不够时只在同一用户的其他会话补充。画像异步由模型提取并存入专属 collection。

另一份 Redis 状态保存未完成计划、行动与证据。**会话记忆**用于给模型提供背景；**计划状态**用于精确恢复流程，两者职责不同。`memory_used` 只报告读到多少最近消息、历史命中数、摘要/画像是否使用，不包含原始敏感内容。

### 3.8 加安全边界

`Pydantic` 限制请求长度；`_redact()` 在模型调用和记忆写入前处理常见 Bearer/API Key 字符串；沙箱只提供脱敏记录；工具白名单和固定参数来源限制越权行动。创建工单还需当前对话明确提出或确认，否定表达会取消待执行工单步骤。工单摘要只包含目标和已核验来源。

这些是**演示级防护**。当前 `user_id` 是客户端自报，查询运行记录只对比字符串，不能当作真实身份认证；脱敏依赖正则，不能保证覆盖所有凭据形式。不要输入真实密钥或生产日志。

### 3.9 暴露 API 与构建 Vue 界面

`POST /developer/chat` 接收 `message`、`user_id`、可选 `conversation_id`；返回 `run_id`、答复、计划步骤、行动、时间线、证据、记忆摘要、`decision_mode`、可选 `ticket_id`。`GET /developer/runs/{run_id}?user_id=...` 读取 24 小时内的运行记录。

Vue 首页直接访问开发者助手的 Python API，提供三条起始案例，显示计划目标和状态、步骤所需证据、行动与观察、时间线、记忆使用情况、工单编号及模型/规则降级标记。页面是在 HTTP 响应到达后渲染完整时间线；**尚非逐事件 SSE/WebSocket 流式更新**。

### 3.10 建立测试和评测记录

`tests/test_developer_assistant.py` 使用模拟模型、模拟 Redis/记忆和 ASGI 模拟平台，覆盖 30 条固定案例，以及跨轮恢复、失败追问、工单幂等、否定授权、脱敏、模型降级等。实测三类真实模型 HTTP 请求、Vue 构建和浏览器交互记录见 [evaluation_report.md](evaluation_report.md)。报告只写已测到的结果，不引用原简历模板中的未经验证指标。

## 4. 与图片逐一对应：十个模块

### 4.1 大模型核心 / Brain

**当前职责**：模型判断问题类型与目标，给出候选工具计划，并在每步选择当前可执行行动；接口是 Anthropic SDK 与可配置兼容服务。使用 `DEVELOPER_MODEL_MODE=rules` 时完全由本地规则模型替代。**边界**：最终结论是对已验证观察的确定性整理；模型不直接执行 HTTP，也不拥有完整控制权。对应 `developer/assistant.py:AnthropicDecisionModel`、`RuleDecisionModel`。

### 4.2 记忆 / Memory

**短期**：Redis 最近对话、24 小时压缩摘要和待完成计划；**长期**：ChromaDB 情景记忆与用户画像；**外置知识**：ChromaDB v1 文档和模拟平台记录。文档检索是 RAG，不等同于用户记忆。跨用户查询使用 `user_id` 过滤，但正式多租户还需要身份认证和存储层权限。对应 `memory/conversation_memory.py`、`mcp/knowledge_base.py`。

### 4.3 规划 / Planning

模型输出目标和工具建议，服务端保留合法顺序、补全证据链，形成带 `id`、`required_evidence`、`status` 的步骤。401/403、429、Webhook 各有最小证据链；模型可从满足依赖的步骤中选下一行动；失败后最多修订一次，缺少标识时等待。它具备受约束的 Plan-and-Execute 和 ReAct 风格流程；**没有 Tree-of-Thought，也没有开放式计划搜索**。对应 `KIND_TO_TOOLS`、`_approved_tools()`、`_ready_steps()`、`DeveloperAssistant.run()`。

### 4.4 工具调用 / Tool Use

五个本地注册工具完成文档检索、请求记录、密钥权限摘要、Webhook 投递和模拟工单创建。模型返回 JSON 行动提议，应用层验证并调用。**Function Calling 和 MCP 协议是图片中的可选实现路线，本场景没有接入它们**。也未提供代码执行、浏览器、OCR 或文件读写工具，因为排障场景不需要这些能力。

### 4.5 执行引擎 / Execution

执行器把工具参数映射到沙箱 HTTP 请求，把工单写入模拟服务的 SQLite；工具管理层负责超时和熔断。不会让 Agent 运行 shell、Docker 命令或任意代码。图片中“代码运行/文件编辑”是通用 Agent 的能力示例，不是本场景的验收项。

### 4.6 观察与反馈 / Observation

工具结果被记为成功/失败、摘要、来源和耗时，并进入下一次 `choose_action()` 的状态上下文。请求/投递缺失或文档为空时，回答只说明已有证据并追问，不能虚构记录。Vue 展示观察摘要，不显示模型内部推理文本。

### 4.7 状态与调度 / Scheduler

`DeveloperAssistant.run()` 是单请求串行调度循环，状态包括 `running`、`waiting`、`complete`，步骤包括 `pending`、`done`、`failed`、`waiting`、`cancelled`。五次行动上限和一次修订上限阻止无界循环；Redis 保存等待状态。首版没有多 Agent 协作调度、分布式任务队列或会话级并发锁。

### 4.8 提示词工程 / Prompting

系统提示词 + 开发者 Skill 约束角色、安全边界和 JSON 输出；用户消息、记忆文本、计划和观察按任务拼入提示。应用层再验证 JSON 字段和工具绑定。提示词帮助模型遵循流程，但不能替代后端参数校验与授权判断。

### 4.9 安全与权限 / Guardrail

已实现工具白名单、输入截断、常见密钥脱敏、工单明确授权、标识符来源约束、模拟数据标记与简单用户隔离。尚无 OAuth/JWT、真实租户权限、审计留存策略、提示注入专门测试或细粒度 API RBAC，因此不能称为可直接接入生产数据的安全体系。

### 4.10 输出与交互 / UI

API 返回结构化计划、行动、观察、证据和自然语言答复；Vue 格式化展示并保留 `conversation_id`。已实现最终响应后的时间线展示，尚无实时流式输出。`GET /developer/runs/{run_id}` 便于复查一次运行，但不是永久审计平台。

## 5. 本地构建、启动和验证

以下以 Windows PowerShell 为例；在独立终端按顺序执行。配置文件只放本地 `backend/.env`，不要把真实密钥写进文档或提交到 Git。Docker Desktop 需要先启动。

### 5.1 配置模型

在 `backend` 目录复制 `.env.example` 为 `.env`，填入有效的 `ANTHROPIC_API_KEY`、`ANTHROPIC_MODEL`；若是兼容服务，还需 `ANTHROPIC_BASE_URL`。文件已存在时直接编辑，避免覆盖。真实模型模式是默认值；无可用模型时可在 Compose 环境中设置 `DEVELOPER_MODEL_MODE=rules` 做确定性演示，但报告必须把它标为规则模式。

### 5.2 启动 Python 栈

~~~powershell
Set-Location '<仓库路径>\backend'
docker compose up -d --build devtrace
docker compose ps
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8100/health
~~~

`devtrace` 会启动依赖的 Redis、ChromaDB 和模拟平台。首次构建需下载 Python 依赖及 ChromaDB 默认 embedding 模型；若已有 8000 或 8100 端口占用，请修改 Compose 端口映射或停用冲突服务。

### 5.3 调用 API

~~~powershell
$body = @{ message = '请求 req_auth_01 返回 401，帮我排查'; user_id = 'demo' } | ConvertTo-Json
$result = Invoke-RestMethod -Uri 'http://127.0.0.1:8000/developer/chat' -Method Post -ContentType 'application/json' -Body $body
$result.decision_mode
$result.plan
$result.actions
$result.evidence
~~~

同一会话第二轮把返回的 `conversation_id` 传回。例如先说“我的 API 返回 401”，再补充“`request_id` 是 `req_auth_01`”。查看一次运行：`GET /developer/runs/{run_id}?user_id=demo`。Swagger 位于 `http://127.0.0.1:8000/docs`。

可依次试验：

| 输入 | 预期重点 |
| --- | --- |
| `请求 req_auth_01 返回 401，帮我排查` | 3 个取证工具，文档/请求/密钥前缀证据 |
| `请求 req_quota_01 遇到 429，如何处理` | 读取 `retry_after_seconds`，建议等待 |
| `Webhook 投递 delivery_01 失败，请排查` | 文档 + 投递记录 |
| `req_auth_99 返回 401` | 记录不存在，计划等待补充 |
| `请创建工单`（沿用已有会话） | 有明确请求才创建模拟工单；重复请求编号不变 |

### 5.4 启动 Vue 开发界面

在另一个终端运行：

Set-Location '<仓库路径>\frontend'

npm run dev
~~~

访问 `http://localhost:5173`，即可使用开发者助手。Vite 默认把 `/api/python` 代理到 `http://localhost:8000`。若后端在 18001，**启动 Vite 前**设置 `$env:VITE_PYTHON_API_URL='http://127.0.0.1:18001'`，再运行 `npm run dev`。

Set-Location '<仓库路径>\backend'
python -m pytest -q tests

或在一次性 Docker 容器中安装测试依赖后运行同一命令；本次实际执行方式与结果见 [evaluation_report.md](evaluation_report.md)。前端检查：

~~~powershell
Set-Location '<仓库路径>\frontend'
npm ci

~~~

30 条固定案例主要验证**规则参考模型和工具执行器**，不能替代真实模型评测。启动规则与模型两个 HTTP 服务后，可用 `python -m developer.evaluate --base-url <服务地址> --mode rules` 跑全量案例，或用 `--mode model --sample-per-family 1` 对三类故障各抽一条；两者采用同一通过条件。真实模型验证需检查 `decision_mode=model`、计划完成、工具成功和证据引用，同时记录降级次数；不要只凭 HTTP 200 判断模型规划成功。逐条 JSON 和实测分母见 [evaluation_report.md](evaluation_report.md)。

### 5.6 常见排障

| 现象 | 检查 |
| --- | --- |
| API 启动失败 | `.env` 是否配置有效模型密钥；Redis/ChromaDB 是否健康；端口是否冲突 |
| `rules_fallback` | 模型 HTTP 状态、输出 JSON 格式或 token 上限；工具成功不等于模型成功 |
| 查询返回 `waiting` | 是否缺少 `request_id` / `delivery_id`；下一轮是否沿用同一 `conversation_id` |
| 文档没有命中 | `developer_knowledge` 是否初始化、ChromaDB 是否可用、查询是否包含正确故障类别 |
| 前端无法访问 API | Vite 代理目标与当前后端端口是否一致；Docker 前端还需检查 Nginx 运行时配置 |
| 画像/历史没有命中 | 首轮不会天然有历史；画像是后台异步更新，历史片段要等压缩写入后才能召回 |

## 6. 面试展示顺序

先展示 401：输入标识 → 初始计划 → 文档/请求/权限三步 → 证据引用 → 模拟平台结论。再展示缺少标识的跨轮恢复、错误标识触发计划调整和工单明确授权。最后说明 429 与 Webhook 复用同一执行框架，只改变取证链，并打开 [工程化审查.md](工程化审查.md) 主动讲清当前边界。

准确表述：“我构建了独立的单主 Agent 开发者排障项目，使用模型提出计划和逐步行动，服务端强制最小证据链；Redis/ChromaDB 负责跨轮记忆，HTTP 模拟平台提供可复现观察，前端展示计划状态和证据。30 条规则案例与三类真实模型请求已测，生产接入所需的身份认证、租户权限和持续评测仍是后续工作。”
