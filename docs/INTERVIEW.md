# DevTrace 面试问答（12 题）

> 用法：不要背全文，记住“结论 → 证据 → 边界”三段。所有数字以仓库 tag `demo-2026-10-23.1` 为准。

## Q1. 用 60 秒介绍这个项目

**结论**：DevTrace 是一个面向开发者平台 API 接入排障的受约束单 Agent，覆盖 401、429、Webhook 失败三类问题。

**展开**：它把计划生成、候选评分、工具白名单、证据诊断、分层记忆、SSE 流式任务、Redis 队列、RBAC/审计、workspace 隔离串成一条可回放链路；本地模拟平台提供数据，不连接真实平台。

**证据**：十个模块、371 项测试 + 219 subtests、CI 全绿；40 条 holdout 规则 40/40、真实模型 37/40；最终 tag `demo-2026-10-23.1`。

**边界**：演示级，不是生产系统；生产身份/TLS/WORM/HA 未做。

## Q2. 为什么是单 Agent，不做多 Agent？

**结论**：这个问题的瓶颈不是“并行度”，而是“证据可信 + 行为可审计”。

**理由**：
- 排障需要严格依赖顺序（先记录后文档、先 trace 后 scope），多 Agent 会引入谁改了什么状态的问题；
- 单 Agent + 服务端计划约束，能把每一步观察、失败、重规划和证据来源写进同一条时间线；
- 多 Agent 的收益（并行探索、辩论）在 3 类固定问题上不明显，成本是调试和审计复杂度。

**边界**：如果问题域扩展到多平台/多工单并发，才值得引入 planner-worker 或多 Agent；现在没做，不冒充。

## Q3. 计划是怎么被约束的？

**结论**：模型只提议，服务端批准；批准后每一步还要过依赖/门禁。

**机制**：
- `planner.py` 维护 `KIND_TO_TOOLS`、`TOOL_DEPENDENCIES`、`TOOL_EVIDENCE`；
- 候选计划评分按证据覆盖、记录先于文档、依赖合法、长度打分；
- `_approved_tools` 只允许白名单工具；`_ready_steps` 检查 issue_id、key_prefix、ticket_authorized、版本观察等门禁；
- 工具参数由服务端从用户输入/已观察记录派生，模型不能自报用户/密钥/工单 ID。

**证据**：`tests/test_developer_assistant.py`、`tests/test_holdout_cases.py`；候选计划评测 11/11。

## Q4. 工具调用怎么保证安全？

**结论**：三层——白名单、参数来源、副作用授权。

- 白名单：计划只批准允许的工具；MCP 工具也只注册只读工具；
- 参数来源：请求 ID、密钥前缀、关联请求 ID 来自用户输入或观察记录，不由模型自由填；
- 副作用：`create_support_ticket` 必须用户显式授权，保留在本地，不迁到 MCP；幂等键防重复；
- 脱敏：工具结果中的 Key 只显示前缀，审计不记录正文/完整 Key。

**边界**：这是应用层约束，不是完整沙箱；生产还要网络隔离、最小权限凭据、审计 WORM。

## Q5. 为什么 `create_support_ticket` 不迁移到 MCP？

**结论**：写操作需要“只有本服务持有”的授权与幂等上下文。

- 工单要用户明确授权，授权状态在服务端；
- 工单需要会话/幂等键，不能变成 MCP 参数让模型或第三方自报；
- 写副作用走远程传输后，证据链里无法区分“谁执行了副作用”。

所以 MCP server 只托管 8 个只读工具；工单始终本地。这是有意的安全边界，不是迁移没做完。

## Q6. 记忆质量怎么评测？为什么 strict 6/10 而 semantic 10/10？

**结论**：两列都报告，主门槛只看 semantic；strict 保留作对照，不掩盖。

- strict：请求编号、`密钥前缀:权限`、结论整句逐字命中 → 6/10；
- semantic：编号仍逐字；权限允许同义动作；结论按概念组命中，命中前做否定检查（“未过期”不算“过期”）→ 10/10；
- 0 编造标识符、0 超长摘要；4 场 strict 失分逐条核对是标点合并/同义替换，不是事实丢失。

**边界**：10 场合成对话、单 provider、作者模板；semantic 满分不等于事实完整复述；不把评测放进 CI（真实调用成本/不稳定）。

## Q7. 队列可靠性怎么做的？

**结论**：Redis List + ZSET + 租约 + 死信，不引入新中间件。

- 优先级 high/normal/low + legacy 兼容；
- worker 用 `BRPOP` 按优先级领取；
- 任务带 `lease_id/lease_until`，每 30s 续租；租约过期用 `SET NX` 互斥回收；
- 失败进延迟 ZSET（1s/2s/4s，上限 30s），耗尽进死信；管理员可重放；
- 会话锁值存 `task_id`，终态释放用 Lua 比较删除，晚到清理不会误删新任务。

**证据**：`test_queue_production.py`、P12 真实 `docker kill` 时间线、P13/P14 锁语义测试。

## Q8. 你遇到最难的一个 bug？

**STAR**：
- **S**：流式诊断客户端断开后，任务偶尔停在 `running`，会话锁要等 180s TTL；
- **T**：定位为什么取消没有生效，且不能靠“加大 sleep”掩盖；
- **A**：根因是 Python 3.10 `asyncio.wait_for(queue.get(), 15)` 在内部 future 已完成时会吞掉一次外部 `Task.cancel()`；改成 `asyncio.wait` + 常驻 getter，超时不取消内层任务，finally 显式取消；加了确定性对照用例（旧写法不抛、新写法抛）；
- **R**：取消能传播、记录 `cancelled`、锁释放；事件顺序/心跳/150s 上限不变。

**教训**：概率性 bug 不能靠单次绿灯判断；要有确定性对照 + 循环验证。

## Q9. `kill -9` 恢复怎么验证的？

**结论**：真杀执行中的 worker，不是注入假租约。

- 隔离栈 2 worker、lease 30s、worker `restart: "no"`；
- 任务进入 `running` 后 1.22s `docker kill`（exit 137），幸存 worker 在租约到期后 3.12s 回收；
- `attempts 0→1`、唯一终态、`run_id` 唯一、`task.finished` 恰 1 条、会话锁释放、同会话可重新请求；
- 终态是 `waiting`，不是 `completed`——不把合法第三终态包装成成功。

**代价**：真实模型调用 7 次，超过原计划 2 次；原因是按“运行次数”而非“provider 调用次数”估预算。已如实写进报告。

## Q10. 真实模型 holdout 只有 37/40，为什么？

**结论**：3 条失败逐条分类，不删样本、不改断言。

- 2 条 public_api：实际工具是 `mcp_lookup_error_playbook` / `mcp_search_public_docs`，标签按本地拼写断言 → 标签绑定，不是能力缺失；
- 1 条 v2 文档边界：工具与假设正确，但没带回 v1 文档具体证据；
- 官方 37/40 保留；另做 base 名补充归因 39/40，只解释 `mcp_` 前缀差异，不宣称能力提升。

**边界**：40 条标签作者手写、单 provider；真实模型只跑一遍、不重跑挑结果。

## Q11. 安全/租户/审计做到什么程度？

**结论**：演示级安全边界完整，生产身份/审计/隔离未完成。

- JWT + PBKDF2；管理员由服务端配置判定，角色不进 token；
- workspace 由服务端解析，run/task 跨 workspace 404；记忆按 user+conversation 隔离；
- 审计 Redis Stream，应用层只追加，detail 白名单 + 密钥脱敏；不是 WORM；
- 限流 30/min/user；流式与同步共用配额；Redis 故障 fail-open 并记审计（可用性优先，已写限制）。

## Q12. 如果继续做，下一步是什么？

**结论**：不再加 Agent 花活，先做生产化底座。

顺序建议：
1. 身份/OIDC + 多租户成员 + TLS + 密钥轮换；
2. Redis/Chroma 高可用、备份、容量压测；
3. 审计 WORM/导出、网关级限流；
4. ChromaDB 漏洞迁移评估（pgvector/Qdrant）；
5. 多 provider 评测、外部 MCP 信任模型；
6. 最后才是并行计划/多 Agent。

**一句话**：这个项目证明我能把 Agent 做成可测试、可审计的工程件；生产化是另一条明确的路线，不是靠堆功能。
